- ที่มา: บทที่ 7 ของคู่มือ "Let Claude Edit Your Videos" (แยกชั้นคนออกจากฉาก) · พิสูจน์บน 0917 วันที่ 2026-09-29 ผู้ใช้รับผล ("เหลือนิดหน่อยแต่แค่นี้ก็โอเคแล้ว")

## 1. ที่มา

### 1.1 สิ่งที่พิสูจน์แล้ว

ข้อความเด่นชุดหนึ่งอยู่หลังตัวคน ซับยังอยู่หน้าสุด ทำได้สองทาง พิสูจน์บน 0917 (CapCut 9.5.0) ทั้งคู่

- **ทางของ CapCut (ต้องมี Pro ตอน export):**
  - เขียนสำเนาชิ้นวิดีโอหลักแบบไม่มีเสียงบน track overlay (`flag 2`)
  - วัสดุวิดีโอของสำเนามีสามช่อง:
    - `matting.flag` 3
    - `matting.path` = path เต็ม `<โฟลเดอร์ดราฟต์>/matting/<md5 ของ path ไฟล์สื่อ>`
    - `custom_matting_id` เป็น UUID ตัวพิมพ์ใหญ่ที่สร้างใหม่
  - ตอนเปิดดราฟต์ CapCut คำนวณ mask ในเครื่องเอง (ชิ้นละช่วงต้นฉบับ ±3 วิ ราว 3.4 MB ต่อวินาทีต้นฉบับ เก็บใน `<ดราฟต์>/matting/`)
  - ถ้าใช้ placeholder ที่ id สุ่ม CapCut จะไม่คำนวณ
- **ทางของเราเอง (ไม่ต้องมี Pro):**
  - ทำ mask ทีละเฟรมด้วย Apple Vision `VNGeneratePersonSegmentationRequest` คุณภาพ `.accurate`
  - เกลี่ยขอบด้วย guided filter (r 12 ที่ 1080×1920, eps 1e-3, ใช้ความสว่างของเฟรมนำ)
  - เฉลี่ยตามเวลา ±2 เฟรม น้ำหนัก 1-2-3-2-1 ("ช่อง 4" ที่ผู้ใช้เลือก)
  - ทำเป็นไฟล์ ProRes 4444 ที่มีแต่ตัวคน วางบน track overlay
  - ตอนพิสูจน์ ไฟล์ตัวคนเป็นตาราง 1/30 พอดี แต่เฟรมต้นฉบับอยู่เลยเส้นตารางเล็กน้อย CapCut จึงเลือกเฟรมของสองชั้นไม่ตรงกัน ภาพข้างในตัวคนนำภาพข้างใต้ไปหนึ่งเฟรมจนขอบกระพริบ
    - ตอนนั้นแก้ด้วยการเลื่อนเนื้อไฟล์ไปหนึ่งเฟรม ("เริ่มก่อนหนึ่งเฟรม")
    - ผู้ใช้กำหนดว่าเฟรมต้องตรงกันโดยไม่เลื่อน สเปกนี้จึงให้ไฟล์ใช้เวลาของเฟรมเดิมแทน (§7.2 ข้อ 1)
- **ทั้งสองทาง:**
  - CapCut เรียงชั้นตามลำดับใน `tracks[]` ไม่ใช่ `render_index`
  - ชั้นตัวคนต้องได้ `clip` และ keyframe ซูมของชิ้นหลักด้วย ไม่อย่างนั้นช่วงซูมจะเห็นภาพซ้อน

### 1.2 สิ่งที่วัดได้ระหว่างออกแบบ (2026-09-29)

- **ขนาดไฟล์ทางของเรา:**
  - ตอนพิสูจน์ได้ ~60 MB/วิ
  - ถ้าใช้ `prores_ks` 4444 ของ ffmpeg ที่มากับแอป ตั้ง `-qscale:v 12` · `-alpha_bits 8` · ทำสีเป็นดำตรงที่ alpha เป็น 0 จะได้ **9.75–10.35 MB/วิ** และขอบเหมือนต้นแบบเมื่อขยาย 4 เท่า
  - ตัวเลขนี้วัดจากไฟล์ต้นแบบที่ทำสีดำด้วย Python ต้องวัดใหม่ด้วยขั้นตอน ffmpeg จริงของแอป (§13 ข้อ 3)
- **ทางลดขนาดที่ลองแล้วไม่เลือก:**
  - 720p: ขอบนุ่มจนเห็น
  - ครอปเฉพาะตัวคน: ลดได้แค่ ~1.3% หลังเติมดำ
  - HEVC ที่มี alpha: ffmpeg ของแอปทำไม่ได้ และยังไม่รู้ว่า CapCut เล่นได้ไหม
- **ทำเฉพาะช่วงที่ข้อความขึ้น:** 0917 ครอบ 12.1 จาก 22.2 วิ
- **ตัวตัดคน Swift:**
  - build ด้วย `-target arm64-apple-macos12.0` แล้ว `strip -x` ได้ 80 KB ใช้แค่ไลบรารีของระบบ
  - Vision ใช้ 35–43 ms ต่อเฟรม
  - guided filter กับการเฉลี่ยตามเวลาใน Accelerate ใช้ ~7 ms ต่อเฟรม
  - เวลารวมราว 2 วินาทีต่อวินาทีวิดีโอ เป็นค่าที่คำนวณ ยังไม่ได้วัดทั้งงาน (§13 ข้อ 7)
- **mask ของ Vision** มีขนาดคงที่ 1512×2016 ต้องย่อหรือขยายให้เท่าภาพ
- **ฟุตเทจในดราฟต์ของผู้ใช้** (6 ไฟล์, อ่านอย่างเดียว):
  - ทุกไฟล์เป็น H.264 SDR BT.709 และไม่หมุน
  - 5 ไฟล์เป็น 1080×1920 หรือเล็กกว่า ที่ ~29.9–30.3 fps เฉลี่ย
  - อีก 1 ไฟล์เป็นแนวนอน 27.7 fps
- **ตำแหน่งข้อความตอนนี้:** แบบอัตโนมัติจะหลบหน้า (`keepClear`) ข้อความจึงมักไปตกที่ช่วงตัว ซึ่งตัวคนจะบังเกือบหมด

## 2. การตัดสินใจ

ผู้ใช้เลือก (2026-09-29):
1. ทำ "ตัวหนังสืออยู่หลังคน" เป็นฟีเจอร์จริงก่อนข้ออื่นในบทที่ 7
2. **Claude เลือก** ว่าชุดไหนอยู่หลังคน ผู้ใช้เปิดปิดทีละชุดได้
3. ชุดที่อยู่หลังคนวาง **บนสุด ให้หัวบังขอบล่างของตัวหนังสือบางส่วน** ถ้าบังมากจนอ่านไม่ออกแอปจะเตือน
4. ค่าหลักใช้ **ตัวตัดคนของเรา** แต่ **ถ้าเปิด "มี CapCut Pro" ให้ใช้ตัวลบพื้นหลังของ CapCut แทน**
5. **เฟรมของตัวคนต้องตรงกับภาพข้างใต้ทุกเฟรม โดยไม่ใช้วิธีเริ่มก่อน** ("เฟรมต้องตรงกันไม่เริ่มก่อน") ไฟล์ตัวคนจึงทำเฟรมต่อเฟรมจากเฟรมที่ชั้นหลักแสดง และให้ CapCut อ่านกลางช่องระหว่างเฟรม (§7.2 ข้อ 1 · พิสูจน์แล้ว)

ค่าเริ่มต้นที่ผมตั้ง (ผู้ใช้ตรวจในสเปกนี้):
- ตัดคนไม่ได้: ชุดนั้นถูกวาดไว้หน้าคน และบอกจำนวน (§12)
- **ไม่มีเพดานจำนวน:** ชุดที่ Claude เลือกไม่ถูกจำกัดด้วยตัวเลข เพราะใน M25 ผู้ใช้ตัดสินไว้แล้วว่าไม่มีโควตาหรือเพดานต่อชนิด จำนวนเป็นเรื่องของ Claude กับผู้ใช้ prompt บอกให้ใช้น้อยแทน
- **ลำดับชั้น (§9.1):**
  - ข้อความเด่นชุดปกติกับซับอยู่หน้าสื่อแทรกและกราฟิก ตรงกับที่โค้ดตั้งใจไว้แต่เดิม
  - สื่อแทรกและกราฟิกอยู่หน้าตัวคน
- **เข้ารหัส:** q12 ทำเฉพาะช่วงของชุด คิวแยกจากกราฟิก เริ่มตัดในเบื้องหลัง ไม่ครอป

## 3. ขอบเขต

ทำ:
- ป้าย "อยู่หลังคน" ต่อชุด (Claude เลือก ผู้ใช้แก้ได้) และสวิตช์รวม
- วางชุดที่อยู่หลังคนไว้บนสุด พร้อมคำเตือนเมื่อหัวบังมาก
- ตัวตัดคนของเรา (Swift helper ที่มากับแอป) พร้อมคิว ไฟล์ และการล้างไฟล์
- ทางของ CapCut เมื่อเปิด "มี CapCut Pro"
- การเขียนลงดราฟต์: ลำดับชั้นใหม่, ซูมบนชั้นตัวคน, ตัวเลขในหน้าเขียน
- พิสูจน์ใน CapCut ก่อนเขียนโค้ด (§13)

ไม่ทำในรุ่นนี้:
- วางตำแหน่งตาม mask (หาตำแหน่งที่ตัวคนบังพอดี) ใช้คำเตือนแทนไปก่อน
- HEVC ที่มี alpha และการครอปตัวคน
- ทางของเรากับต้นฉบับที่หมุน, HDR (HLG/PQ/BT.2020) หรือดราฟต์ที่ไม่ใช่ 30 fps ชุดพวกนี้ถูกวาดไว้หน้าพร้อมเหตุผล (§6.2)
- ภาพตัวคนซ้อนจริงในหน้าตัวอย่างของแอป (Chromium เล่น ProRes ที่มี alpha ไม่ได้) ใช้ป้ายแทน
- ให้ตัวคนบังอย่างอื่นนอกจากข้อความเด่นที่อยู่หลังคน

ลำดับงาน: ทุกขั้นจบด้วยเทสต์เขียว
1. พิสูจน์และทำ fixture (§13)
2. ตัวตัดและคิว
3. การเขียนและลำดับชั้น
4. Claude และหน้าจอ
5. ทางของ CapCut

## 4. ข้อมูลที่เก็บ

- **`GroupLook.behindPerson?: boolean`** (`packages/core/src/flair/plan.ts`) ถ้าไม่มีค่าเท่ากับ false
  - เก็บต่อชุดใน `StoredOutline.flair.looks`
  - `regroupFlair` `withoutLine` `withLineText` ส่งต่อได้อยู่แล้ว เพราะ spread ลุคทั้งก้อน
  - จุดที่ต้องแก้ให้ไม่ทิ้งช่องใหม่:
    - `enforce` (ทาง non-edited)
    - `setLook` ใน `main/flair.ts` (สร้างทีละช่อง ต้องเก็บทุกช่องที่ patch ไม่ได้ส่งมา)
    - `acceptHighlights` ใน `pick.ts`
    - IPC validation ใน `highlight-api.ts` (ต้องปฏิเสธค่าที่ไม่ใช่ boolean)
    - `FlairLookPatch` ใน `shared/api.ts`
  - ผู้ใช้เปิดปิดเองนับเป็นการแก้ลุค (`edited`) ผลเหมือนแก้ลุคอื่น คือชุดนั้นเป็นของผู้ใช้ การคิดใหม่ไม่ทับ
- **`FlairOptions.behindPerson: boolean`** เป็นสวิตช์รวม ค่าเริ่มต้น **true**
  - เพิ่มใน `DEFAULT_FLAIR_OPTIONS` · sanitiser ใน `settings.ts` (`read()` สร้างทุกช่องใหม่ ต้องเก็บ false ไว้ด้วย) · IPC checks ใน `highlight-api.ts` และ `timeline-api.ts`
  - เครื่องที่อัปเดตมาได้ค่า true
  - ปิดสวิตช์: ไม่มีชุดไหนอยู่หลังคน ทั้งตอนแสดงและตอนเขียน แต่ป้ายต่อชุดยังเก็บอยู่
- **ป้ายที่มีผล** = `look.behindPerson` ที่เก็บไว้ && `flair.behindPerson` && ระดับแสดงชุดนั้น
  - ป้ายนี้ไม่ขึ้นกับ `flair.text` (สวิตช์ลุคข้อความ): ต้องอ่านจากลุคที่เก็บไว้ ไม่ใช่จาก `looksInForce` ซึ่งคืน `DEFAULT_LOOK` เมื่อปิดลุคข้อความ
  - คำนวณครั้งเดียวในฟังก์ชันเดียว แล้วส่งให้ทุกที่ที่ใช้ (§5.3)
- ไฟล์ตัวคนไม่เก็บในโครงเรื่อง หาได้จาก hash (§7.4) เหมือนกราฟิก

## 5. Claude เลือกชุด และตำแหน่ง

### 5.1 prompt ข้อความเด่น

- คำตอบต่อชุดมีช่อง `behindPerson` (boolean, `.default(false)` และ `?? false` ตอนอ่าน แบบเดียวกับ `tone`)
- ข้อความที่ส่งให้ Claude เพิ่มข้อมูลภาพของแต่ละจุด: ฉากนั้นเห็นหน้าคนไหม และหน้าอยู่ตรงไหน
  - ข้อมูลมาจาก `keepClear` และชนิดฉากที่วิเคราะห์ไว้แล้ว ทำแบบที่ `graphics/direct.ts` ส่งให้ส่วนกราฟิก
- แนวทางใน prompt:
  - เลือกเฉพาะจังหวะสำคัญ ข้อความสั้น ตัวใหญ่ บนฉากคนพูดหน้ากล้องที่เห็นคนชัด
  - ไม่เลือกบนฉากที่ไม่มีคน หรือช่วงสื่อแทรก
  - ใช้น้อย เพื่อให้เป็นจุดเด่น
- ขึ้น `HIGHLIGHT_PROMPT_VERSION` ใหม่ และแก้เทสต์ที่ตรึงค่าไว้
- ถ้าสวิตช์รวมปิด ก็ยังขอคำตอบนี้จาก Claude เพื่อให้เปิดทีหลังได้โดยไม่ต้องคิดใหม่

### 5.2 ระดับความจัด

ระดับยังทำงานเหมือนเดิม ชุดที่ระดับซ่อนจะไม่ถูกตัด ไม่ถูกเขียน และไม่ถูกนับ

### 5.3 ตำแหน่ง

- ชุดที่ป้ายมีผลใช้ตำแหน่ง **บนสุด** เสมอ ไม่ว่าตำแหน่งข้อความเด่นในตั้งค่าจะเป็นอะไร
  - ใช้ขอบบนที่ `TOP` = 0.72 ในหน่วยของ CapCut (+1 คือขอบบน −1 คือขอบล่าง) ราว 14% จากขอบบนจอ
  - ไม่หลบหน้า
- **ตำแหน่งขึ้นกับสิ่งที่รู้ก่อนตัดเท่านั้น** คือป้ายที่มีผล, ทางที่ใช้, มีตัวตัดไหม และคุณสมบัติต้นฉบับ (§6.2)
  - ไม่ขึ้นกับผลของงานตัด (สำเร็จ ล้มเหลว ไม่เจอคน)
  - ชุดที่ตัดไม่สำเร็จจึงยังอยู่บนสุด แต่ถูกวาดไว้หน้าคน (§12) แถบข้อความที่กราฟิกหลบจึงไม่ขยับตามผลงาน และตัวอย่างกับการเขียนได้ตำแหน่งเดียวกัน
  - ชุดที่รู้ตั้งแต่ก่อนตัดว่าใช้ทางของเราไม่ได้ (ไม่มีตัวตัด หรือต้นฉบับไม่รองรับ) ป้ายไม่มีผล จึงวางตามปกติ
- ส่งป้ายที่มีผลไปทุกที่ที่เรียก `placementOf`:
  - การหลบของตัวอย่าง (`highlights.ts` `dodgeOf`)
  - `textBands` ของกราฟิก (`graphics-cues.ts`) ทั้งตอนตัวอย่าง ตอนเขียน และในรายการแถบที่ส่งให้ prompt กราฟิก (`main/flair.ts`)
  - การเขียน (`timeline.ts`)
- กราฟิกยังหลบแถบของชุดนี้เหมือนชุดอื่น

## 6. ช่วงเวลา และต้นฉบับที่รองรับ

### 6.1 ฟังก์ชันเดียวสำหรับช่วงของตัวคน

`cutoutRanges(plan, fps, placedGroups, ...)` ใน core เป็นฟังก์ชัน pure ไม่ต้องใช้ดราฟต์:
- ทำการปัดเฟรมเหมือน `buildRoughCut` (`usToFrame` ของจุดเริ่มต้นฉบับของแต่ละชิ้น และตัวนับเฟรม) และเหมือน `addHighlightTracks` (การปัดบรรทัดแรกกับจุดจบ รวมถึงบรรทัดที่ไม่มีเฟรมเต็ม)
- ผลต่อชุด ต่อชิ้นหลักที่ชุดทับ: ช่วงบนไทม์ไลน์ และช่วงในต้นฉบับ เป็น **เลขเฟรมเต็มบนตารางของ fps ดราฟต์** คือเฟรมเริ่มกับจำนวนเฟรม
- ช่วงที่ทับกันสั้นกว่าหนึ่งเฟรมถูกข้าม
- ใช้ที่เดียวทุกจุด: การส่งงานจากตัวอย่าง, สถานะในตัวอย่าง, การรอในการเขียน, ตัวเขียน, การลองใหม่ และ hash
- เทสต์: hash ของงานจากตัวอย่างต้องเท่ากับของการเขียน บนการตัดที่มีจุดเริ่มต้นฉบับหลายแบบ และบรรทัดที่ไม่มีเฟรมเต็ม

### 6.2 ต้นฉบับที่ทางของเรารองรับ

ตรวจด้วย ffprobe ที่มากับแอป เก็บผลไว้ตาม path, ขนาด และเวลาแก้ของไฟล์ แล้วรู้ผลก่อนตัดเสมอ

รองรับเมื่อผ่านทุกข้อ:
- fps ของดราฟต์ = 30 (ที่พิสูจน์แล้ว)
- ไม่มีข้อกำหนดเฟรมเรตของต้นฉบับ เพราะไฟล์ตัวคนทำเฟรมต่อเฟรมจากสิ่งที่ชั้นหลักแสดง (§7.2 ข้อ 1) เฟรมซ้ำหรือข้ามของต้นฉบับก็ตามไปด้วย
- ไม่หมุน (ไม่มี rotation side data หรือเป็น 0)
- SDR: `color_transfer` ไม่ใช่ `arib-std-b67` หรือ `smpte2084` และ `color_primaries` ไม่ใช่ `bt2020`
- ffmpeg ถอดรหัสได้

ถ้าไม่ผ่าน ป้ายไม่มีผลสำหรับชุดนั้น ชุดนั้นวางและวาดตามปกติ นับเป็น `front` และสถานะบอกเหตุผล

- ต้นฉบับ 0917 (`IMG_9646.MOV`, avg 29.993 และมีบางช่วงที่ห่าง 21/600) ต้องผ่าน มีเทสต์ของกฎนี้
- ชนิดต้นฉบับ (เฟรมห่างเท่ากันหรือไม่) ดูจากรายการ pts ที่ ffprobe (หรือ AVFoundation ใน helper) อ่านได้ ใช้เลือกกฎใน §7.2 ข้อ 1
- ทางของ CapCut ไม่ใช้การตรวจนี้ เพราะ CapCut จัดการเอง

## 7. ตัวตัดคนของเรา (เมื่อปิด "มี CapCut Pro")

### 7.1 โปรแกรม `boxblack-segment`

- **ซอร์สและการ build:**
  - ซอร์สที่ `apps/desktop/native/segment/main.swift`
  - build ด้วย `apps/desktop/scripts/build-segment.sh <out>` คือ `xcrun swiftc -O -target arm64-apple-macos12.0`, `strip -x`, ตรวจ `--version` แล้วได้ `apps/desktop/resources/bin/boxblack-segment`
  - `VERSION` ตรึงไว้ในสคริปต์
- **คำสั่ง:**
  - `boxblack-segment --version`
  - `boxblack-segment masks --frames <dir> --out <dir> --width W --height H [--radius R]`:
    - อ่าน JPEG ตามลำดับชื่อ
    - Vision `.accurate` → ย่อหรือขยาย mask เป็น W×H แบบ bicubic
    - guided filter r = R (ค่าเริ่มต้น 12 × ด้านสั้น/1080), eps 1e-3, ใช้ความสว่างของเฟรมนำ, ขอบแบบ edge-extend
    - เฉลี่ยตามเวลา 1-2-3-2-1 ±2 เฟรม (ที่ปลายช่วงใช้เฟรมสุดท้ายซ้ำ)
    - เขียน PNG เทา 8 บิตชื่อเดียวกับเฟรม
    - ออกทาง stdout เป็นบรรทัด: `progress <done> <total>` และ `coverage <สัดส่วนพื้นที่ mask เฉลี่ย>`
  - `boxblack-segment masks --raw-masks <dir> ...` ใช้ในเทสต์เท่านั้น: ข้าม Vision แล้วใช้ mask ดิบที่ให้มา เพื่อเทียบการย่อขยาย guided filter และการเฉลี่ยตามเวลาได้ผลแน่นอน
  - `boxblack-segment sample --frames <dir> --size S`:
    - ใช้ Vision ทำ mask ของเฟรมที่ให้ ย่อเป็นด้านยาว S (ค่าเริ่มต้น 256)
    - ออกทาง stdout เป็น JSON บรรทัดละเฟรม `{ "frame": ชื่อ, "width", "height", "mask": base64 ของ 8 บิต }` ใช้กับคำเตือนหัวบัง (§10)
  - error และวิธีใช้ออกทาง stderr และ exit ไม่ใช่ 0
- **ของที่ต้องเพิ่มตามแบบ ffmpeg และ whisper-cli:**
  - `release-check.ts`: ต้องมีไฟล์นี้ และ VERSION ตรงกับที่ตรึงไว้ พร้อมข้อความสำเร็จและเทสต์ของมัน
  - `bundled-segment.test.ts`: `otool` ลิงก์แค่ไลบรารีของระบบ · `minos 12.0` · arm64
  - หา path ผ่าน `join(resourcesDir, "bin")` ทั้งตอน dev และตอนแพ็ก ไม่ใช่ `process.resourcesPath` ซึ่งตอน dev ไม่มี `bin`
  - `ToolReport.segment` กับแถวในตั้งค่า "เครื่องมือบนเครื่องนี้": ไม่นับใน `anyMissing` และไม่มีคำแนะนำ Homebrew
  - ถ้ารันไม่ได้ (เช่น Open Anyway ไม่ครอบคลุม) ถือว่า "ไม่มีตัวตัด" (§12)

### 7.2 งานหนึ่งชิ้น

หนึ่งงานคือหนึ่งช่วงจาก `cutoutRanges` (หนึ่งชุด × หนึ่งชิ้นหลัก) ทำตามลำดับนี้

1. **เฟรมตรงกับชิ้นหลักทุกเฟรม โดยไม่เลื่อน** (ผู้ใช้กำหนด 2026-09-29: "เฟรมต้องตรงกันไม่เริ่มก่อน" · พิสูจน์แล้ว §13):
   - **CapCut เลือกเฟรมคนละแบบตามชนิดไฟล์** (วัดด้วยไฟล์รหัสแถบและ export สองรอบของ 0917):
     - CapCut ถามแต่ละชิ้นที่เวลา `source.start + (t − target.start)` ทุกเฟรมบนไทม์ไลน์
     - ไฟล์ที่ทุกเฟรมยาวเท่ากัน (ไฟล์ ProRes ของเรา): แสดง **เฟรมแรกที่เวลาไม่ก่อน** จุดที่ถาม (ปัดขึ้น)
     - ไฟล์ที่เฟรมห่างไม่เท่ากัน (ต้นฉบับ iPhone): แสดง **เฟรมล่าสุดที่เวลาไม่เกิน** จุดที่ถาม บวกได้ราว 1 µs (ปัดลง)
     - ไฟล์ที่ใช้เวลาเดิมของต้นฉบับจึงไม่ตรง: รอบแรกตัวคนนำไปหนึ่งเฟรมทุกช่วงที่เฟรมไม่ตรงเส้นตาราง
     - กฎนี้อธิบายผลรอบแรกได้ครบ 230/230 เฟรมทั้งสองชั้น
   - **วิธีที่ใช้:**
     - ไฟล์ตัวคนมีหนึ่งเฟรมต่อหนึ่งเฟรมบนไทม์ไลน์ เป็น 30 fps คงที่ พอดี (pts = 20·n ใน timescale 600)
     - เฟรม j+1 ของไฟล์ = เฟรมต้นฉบับที่ชิ้นหลักแสดงที่เฟรม j ของช่วง
       - คำนวณด้วยกฎของชนิดต้นฉบับ: ปัดลง +1 µs สำหรับต้นฉบับที่เฟรมห่างไม่เท่ากัน, ปัดขึ้นสำหรับต้นฉบับที่เฟรมห่างเท่ากัน (ชนิดนี้ยังไม่ได้ลองเป็นชั้นหลัก ถ้าต้นฉบับเป็น 30 fps และจุดตัดอยู่บนเส้นตาราง สองกฎให้ผลเท่ากัน)
     - เฟรม 0 เป็นสำเนาของเฟรม 1 (สำรองไว้)
     - ชิ้นตัวคนในดราฟต์ตั้ง `source.start = 16,667` µs ทุกเฟรมบนไทม์ไลน์จึงถามกลางช่องก่อนเฟรมที่ต้องได้ ห่างขอบทั้งสองข้าง 16.7 ms การปัดของ CapCut จึงไม่มีผล
     - ในรายการอาจมีเฟรมต้นฉบับซ้ำหรือข้ามเมื่อต้นฉบับไม่ใช่ 30 fps พอดี ทำตามรายการเสมอ
   - **ผลรอบสอง:** ตรงกันทุกเฟรม ได้แก่ 41, 69, 12, 64 (มีจังหวะเฟรมไม่เท่า) และ 44 (ซูมช้า) · ช่วงซูมเด้ง 85 เฟรม ตัวคนตรงกับเฟรมที่ควรเป็นทุกเฟรม · ขอบหัวตอนซูมไม่มีภาพซ้อน
   - ได้รายการ `j → เลขเฟรมต้นฉบับ` ใช้ทั้งกับภาพที่ส่งให้ Vision และภาพสีในไฟล์ จึงจับคู่ถูกโดยโครงสร้าง
2. **ภาพให้ Vision:** ffmpeg ดึงเฟรมตามรายการเป็น JPEG `-q:v 2` ที่ขนาดงาน (ข้อ 4) ลงโฟลเดอร์ชั่วคราว
3. **mask:** `boxblack-segment masks`
   - ถ้า `coverage` เฉลี่ยน้อยกว่า 2% (ค่าเริ่มต้น ปรับได้ตอนทดสอบจริง) ถือว่าไม่เจอคน
   - บันทึกผลใน `<hash>.json` แล้วไม่เข้ารหัสต่อ
4. **ขนาดงาน:** ใช้ขนาดต้นฉบับ แต่ถ้าด้านสั้นเกิน 1080 ให้ย่อจนด้านสั้นเป็น 1080 โดยคงสัดส่วน
   - CapCut ปรับวัสดุให้เต็มจอตามสัดส่วนเดิม จึงวางตรงกับชิ้นหลักได้ ตรวจใน §13 ข้อ 3
5. **เข้ารหัส:** อยู่ใน YUV ตลอด จึงไม่มีการแปลงเมทริกซ์สี
   - สีมาจากการถอดรหัสต้นฉบับใหม่ตามรายการเฟรม ไม่ใช่จาก JPEG
   - `format=yuv444p10le` → `alphamerge` กับ mask → เติมสีดำ (Y 64, U/V 512 ใน 10 บิต) **เฉพาะตรงที่ alpha เป็น 0** ด้วย `maskedmerge` กับภาพดำ โดยใช้ mask ที่เป็น 0 ทุกที่ ยกเว้นตรงที่ alpha เป็น 0
   - ห้ามใช้ `premultiply` เพราะทำให้ขอบกึ่งโปร่งใสมืดลง
   - `prores_ks -profile:v 4444 -pix_fmt yuva444p10le -alpha_bits 8 -qscale:v 12 -vendor apl0`
   - คัดลอกแท็กสีของต้นฉบับ (`-colorspace`, `-color_primaries`, `-color_trc`, `-color_range` ตามค่าจาก ffprobe; 0917 เป็น bt709/tv)
   - ไม่มีเสียง
   - 30 fps คงที่: `settb=1/600,setpts=20*N`, `-fps_mode passthrough`, `-enc_time_base:v 1/600` (ถ้าไม่ใส่ ffmpeg จะปัดเวลาเป็น 1/30), `-video_track_timescale 600`
   - เทสต์: pts ในไฟล์ต้องเป็น 20·n ทุกเฟรม
   - ใน filtergraph ห้ามใส่ `\,` ในนิพจน์ที่อยู่ในเครื่องหมาย `'...'` (geq/setpts จะคำนวณผิดโดยไม่ error) และต้องใส่ `format=yuva444p10le` หลัง `alphamerge` เพราะ `alphamerge` ทำงานที่ 8 บิต แล้ว `geq` จะไปทำงานที่ 8 บิตจนค่าดำผิด (พบตอนพิสูจน์)
   - ทางที่แนะนำให้ helper ทำแทน ffmpeg: ถอดรหัสต้นฉบับด้วย AVFoundation (ได้ pts จริงและ YUV) → Vision → กรอง → ใส่ alpha และสีดำ → ส่ง `yuva444p10le` ดิบให้ ffmpeg ที่มากับแอปทาง stdin แค่เข้ารหัส (ffmpeg ที่มากับแอปไม่มี rawvideo muxer จึงส่งเฟรมดิบให้ helper ไม่ได้ ตอนพิสูจน์ใช้ ffmpeg ของ Homebrew ถอดรหัส)
   - เขียนเป็น `.<hash>.partial.mov` ในโฟลเดอร์ตัวคน แล้ว rename เป็น `<hash>.mov` จากนั้นเขียน `<hash>.json` ทีหลังสุดเพื่อยืนยันว่าเสร็จ
   - เทสต์: pixel ที่ alpha อยู่ระหว่าง 1–254 ต้องได้สีเดิม ±2 ระดับ
6. **filter ที่ต้องมี:** เพิ่ม `alphamerge` `maskedmerge` และที่ใช้จริงใน `REQUIRED_FILTERS` (`packages/core/src/media/tool-check.ts`) และในเทสต์ ffmpeg ที่มากับแอป
7. **ไฟล์ชั่วคราว:** อยู่ที่ `tmpdir()/boxblack-cutout/<hash>/` ลบหลังงานเสร็จ ส่วนที่ค้างจากการปิดแอปหรือแอปล่มลบตอนแอปเริ่ม

### 7.3 คิว

- คิวของตัวเอง แยกจากคิวกราฟิก ทำทีละงานข้ามทุกโปรเจค (ไม่ห้ามคิวกราฟิกทำงานพร้อมกัน)
- **รายการที่ต้องการ:**
  - `ensure(folder, jobs)` แทนที่รายการที่ต้องการของโปรเจคนั้นทั้งชุด
  - งานที่ยังไม่เริ่มแต่ไม่อยู่ในรายการแล้วจะถูกเอาออก
  - งานที่กำลังทำอยู่ทำต่อจนจบ ไฟล์ใช้ได้ถ้ากลับมาต้องการอีก
- **ลำดับงาน:**
  1. งานที่การเขียนกำลังรอ
  2. โปรเจคที่ทำตัวอย่างล่าสุด
  3. ที่เหลือ ตามเวลาในคลิป
  - งานที่ hash ซ้ำกันทำครั้งเดียว
- timeout ต่องาน = 30 วิ + 6 วิ × วินาทีของงาน × (จำนวนพิกเซล / 1080×1920) ค่าเริ่มต้นนี้ต้องแก้หลังวัดงานจริง (§13 ข้อ 7) หมดเวลาถือว่าล้มเหลว
- **ปิดแอป:** หยุดงานที่ทำอยู่ ลบไฟล์ชั่วคราว การเขียนที่รออยู่จะล้มเหลวแบบกราฟิก ("หยุดก่อนทำเสร็จ" ดราฟต์ไม่ถูกแก้)
- **ล้มเหลว:**
  - จำไว้ในหน่วยความจำ ลองใหม่ได้จากปุ่มในรายการชุด (แบบ `retryGraphic`)
  - ผล "ไม่เจอคน" จำไว้ใน `.json` จึงไม่ต้องลองใหม่
- **เหตุการณ์ `AppEvent` `"cutout"`:** `{ folder, hash, state: started|progress|failed|done, stage: frames|masks|encode, done, total }`
  - เปอร์เซ็นต์นับเฉพาะขั้น mask ซึ่งกินเวลาเกือบทั้งหมด
  - หน้าจออ่านตัวอย่างใหม่ไม่ถี่กว่าทุก 500 ms เหมือนกราฟิก

### 7.4 ไฟล์

- เก็บในโฟลเดอร์ `~/Movies/CapCut/BOXBLACK/cutouts/` ต้องอยู่ใต้ `~/Movies` เพราะ CapCut เป็น sandbox
- **hash** = 16 ตัวแรก (hex) ของ sha256 จากสิ่งเหล่านี้:
  - path เต็ม ขนาด และเวลาแก้ของต้นฉบับ
  - รายการเฟรมต้นฉบับของไฟล์ (§7.2 ข้อ 1) ช่วงที่ต่างกันแต่ได้รายการเดียวกันจึงใช้ไฟล์เดียวกัน
  - ขนาดงาน
  - `CUTOUT_PIPELINE_VERSION` ใน TS (ขึ้นเมื่อกฎเลือกเฟรม filter หรือการเข้ารหัสเปลี่ยน)
  - VERSION ของ `boxblack-segment` และรุ่นของ ffmpeg ที่มากับแอป
- **hash เปลี่ยนเฉพาะเมื่อช่วงเวลาเปลี่ยน:**
  - แก้คำในบรรทัดโดยไม่เปลี่ยนเวลา ไม่ทำให้ตัดใหม่
  - ที่ทำให้ตัดใหม่: ลบบรรทัดแรก, ตัดคำจนเวลาเปลี่ยน, ชุดถัดไปขยับจนจุดจบของชุดนี้เปลี่ยน, แก้การตัดจนชิ้นขยับ
- ถ้ามีไฟล์ครบอยู่แล้ว (`.json` อ่านได้และ `.mov` มีอยู่) ใช้เลย แม้ตอนนั้นจะไม่มีตัวตัด
- **ตัวบอก "ไฟล์ที่ BOXBLACK ทำ"** ใช้ร่วมกันระหว่างกราฟิกกับตัวคน: ขยาย `isRenderedGraphic` ใน `bin.ts`, `projects.ts`, `flair/media.ts` และรูปแบบชื่อใน `graphics-files.ts` ไฟล์ตัวคนจึงไม่ขึ้นเป็นฟุตเทจหรือสื่อแทรก
- **ตอนเขียน:**
  - `TimelineDeps.cutoutsDir`
  - สร้าง bin item ให้ไฟล์ตัวคนทุกไฟล์ (ขยายจาก `graphicBinItem`)
  - prune ทั้งสองโฟลเดอร์ โดย `playing` = bin id ของกราฟิกรวมกับของตัวคน
- **ล้างไฟล์ในตั้งค่า:**
  - ปุ่มเดิมทำทั้งสองโฟลเดอร์ ใช้กฎ "ใช้อยู่" เดิม
  - "ไม่ว่าง" รวมถึงคิวตัวคนที่ยังไม่ว่าง
  - แถวบอกขนาดกราฟิกกับตัวคนแยกกัน
  - ไม่ลบเอง: ไฟล์ที่เลิกใช้เพราะแก้การตัดสะสมจนผู้ใช้กดล้าง (§15)

### 7.5 เริ่มเมื่อไร

- ทุกครั้งที่ทำตัวอย่าง: `ensure` งานของชุดที่ป้ายมีผลที่ระดับปัจจุบัน
- หลังวางแผนหรือคิดข้อความเด่นใหม่: เหมือนกัน ที่ระดับปัจจุบัน
- **ตอนเขียน:**
  - อ่านตั้งค่าครั้งเดียวที่ต้น `writeNow` ใช้ค่า `pro` นั้นทั้งการตัดสินใจรอ ทางที่ใช้ ตัวเลข แอนิเมชันตอนหายไป และเสียง
  - ตรงนี้ต่างจาก 0.4.2 ที่อ่านหลังรอกราฟิก ถ้าผู้ใช้สลับ Pro ระหว่างรอ จะมีผลในการเขียนครั้งถัดไป
  - รองานของชุดที่จะเขียนและงาน sample (§10) ให้เสร็จหรือล้มเหลวทั้งหมดก่อนอ่านดราฟต์
  - ระหว่างรอ แถวเช็กในหน้าเขียนแสดงความคืบหน้า

## 8. ทางของ CapCut (เมื่อเปิด "มี CapCut Pro")

- ไม่ทำไฟล์ ไม่ใช้คิว ไม่ต้องมีตัวตัด ยกเว้นคำเตือนหัวบัง (§10)
- ไม่มีการตรวจต้นฉบับ (§6.2)
- **ตอนเขียน สำเนาของชิ้นหลักสำหรับแต่ละช่วงใน `cutoutRanges`:**
  - วัสดุวิดีโอ: คัดลอกจากวัสดุของชิ้นหลัก แล้วใส่ id ใหม่ทั้งตัววัสดุและวัสดุเสริมที่ชิ้นอ้างถึง (speed, placeholder ฯลฯ ตามที่ชิ้นหลักมี)
  - `matting.flag` 3
  - `matting.path` = `<โฟลเดอร์ดราฟต์>/matting/<md5>` โดย md5 เป็น hex ตัวเล็กของไบต์ UTF-8 ของสตริง `path` ที่เก็บในวัสดุนั้น
  - `custom_matting_id` UUID ตัวพิมพ์ใหญ่ใหม่
  - เสียง 0 (CapCut เปลี่ยน `has_audio` เป็น true ตอนบันทึก เสียง 0 จึงเป็นตัวที่ทำให้เงียบจริง)
  - keyframe ซูมคัดลอกตรงตัวพร้อม id ใหม่ เพราะใช้ไฟล์และเวลาต้นฉบับเดียวกัน
- ถ้า §13 ข้อ 5 พิสูจน์ว่าสำเนาที่เป็นช่วงกลางชิ้นใช้ไม่ได้ ให้ใช้สำเนาทั้งชิ้นแทน
- ฉากที่ไม่มีคน: CapCut ได้ mask ว่าง ข้อความจึงเห็นเต็มและนับเป็น `laid` ต่างจากทางของเราที่นับ `front` ยอมรับข้อต่างนี้
- สำรองดราฟต์ (`backupDraft`) **ไม่คัดลอก `<ดราฟต์>/matting/`** เพราะ CapCut คำนวณช่วงที่ขาดใหม่เอง ไม่อย่างนั้นทุกการเขียนจะเพิ่มหลายร้อย MB ในโฟลเดอร์สำรอง
- หน้าจอบอกว่า "CapCut จะตัดคนให้ตอนเปิดโปรเจค (ต้องมี CapCut Pro ตอน export)"
- ถ้าเปลี่ยนตัวเลือก Pro หลังเขียน การเขียนครั้งถัดไปจะใช้ทางใหม่ ไฟล์ของทางเรายังเก็บไว้ ล้างได้จากตั้งค่า
- ข้อจำกัดที่ยอมรับ: ผู้ใช้ไม่มี Pro จึงพิสูจน์ได้แค่ว่า CapCut คำนวณ mask และแสดงผลในหน้าตัดต่อ ไม่ได้ลอง export

## 9. การเขียนลงดราฟต์

### 9.1 ลำดับชั้น (`tracks[]` จากล่างขึ้นบน)

1. วิดีโอหลัก
2. แถบของชุดที่อยู่หลังคน
3. ตัวหนังสือของชุดที่อยู่หลังคน (track ของตัวเองต่อบรรทัด)
4. ตัวคน (track overlay `flag 2`)
5. สื่อแทรก
6. กราฟิก
7. แถบของชุดปกติ
8. ตัวหนังสือของชุดปกติ
9. ซับ
10. เสียง

- ใช้ลำดับนี้ทุกครั้งที่เขียน ถ้าไม่มีตัวคนก็ไม่มีชั้น 2–4
- ลำดับนี้คืนสิ่งที่โค้ดตั้งใจไว้แต่เดิม คือข้อความเด่นและซับอยู่หน้าสื่อแทรกและกราฟิก และแก้ปัญหาที่มีอยู่แล้วด้วย: ตอนนี้ซับอยู่ลำดับที่สอง และสื่อแทรกกับกราฟิกถูกต่อท้ายหลังข้อความเด่น ตามกฎ `tracks[]` จึงอาจบังข้อความเด่นและซับ (ต้องพิสูจน์ใน §13 ข้อ 1)
- ตัวเขียนเรียงลำดับครั้งเดียวตอนท้าย แล้วตั้ง `track_render_index` ของทุกชิ้นให้เท่ากับตำแหน่งของ track
  - แก้คอมเมนต์และเทสต์ที่อ้าง `render_index` ให้ตรวจตำแหน่งใน `tracks[]` แทน (`inserts.ts:30`, `graphics.ts:21`, `overlays.ts:62`, `timeline.test.ts` ราวบรรทัด 723 และ 1186)
- แยก lane ของข้อความเด่นเป็นสองกลุ่ม คือชุดหลังคนและชุดปกติ แต่ละกลุ่มจัด lane ตามเลขบรรทัดแบบเดิม
- ชั้นตัวคนเขียนหลัง `addZooms` เพราะต้องใช้ชิ้นหลักที่เขียนแล้วและ keyframe ของมัน

### 9.2 ชิ้นของตัวคน

ต่อหนึ่งช่วงจาก `cutoutRanges`:
- `target` = ช่วงบนไทม์ไลน์ของช่วงนั้นพอดี
- **ทางเรา:** วัสดุวิดีโอของไฟล์ `<hash>.mov` (มีครบ 68 ช่องแบบวัสดุกราฟิก, `has_audio` false, ความยาวตามไฟล์)
  - `source.start` = 16,667 µs (§7.2 ข้อ 1) · ความยาววัสดุ = (จำนวนเฟรมของช่วง + 1) × 33,333 µs
  - `source.duration` = `target.duration`
- **ทาง CapCut:** ตาม §8 ใช้ช่วงต้นฉบับตรงตัว
- ทั้งสองทาง: `clip` คัดลอกจากชิ้นหลัก · เสียง 0 · speed 1
- **ทั้งหมดหรือไม่มีเลยต่อชุด:** ถ้าช่วงใดของชุดวางไม่ได้ (ล้มเหลว ไม่เจอคน ต้นฉบับไม่รองรับ) ชุดนั้นทั้งชุดถูกวาดไว้หน้าคน ไม่เขียนชิ้นตัวคนของชุดนั้นเลย และนับ `front` หนึ่งครั้ง
- ถ้า §13 ข้อ 2 พิสูจน์ว่าเริ่มกลางชิ้นไม่ได้ ให้ใช้ทั้งชิ้นหลักแทน ยังถูกต้องเพราะชุดปกติอยู่เหนือตัวคน แค่ไฟล์ใหญ่ขึ้น

### 9.3 ซูมบนชั้นตัวคน

- ใช้ `value(t)` ของ keyframe แต่ละรายการ (ScaleX, PositionX, PositionY):
  - ก่อน key แรกใช้ค่าของ key แรก
  - หลัง key สุดท้ายใช้ค่าของ key สุดท้าย (CapCut ค้างค่าไว้)
  - ระหว่างนั้นเป็นเส้นตรง (`curveType: "Line"`)
- **ทางเรา:**
  - เวลาในไฟล์ตัวคน = `t_main − (S − 16,667)`
  - เมื่อชิ้นหลักมี keyframe ให้เขียน key ที่จุดเริ่ม (16,667) และจุดจบของช่วงเสมอ ใช้ค่า `value(t)` ณ เวลานั้น แล้วเก็บเฉพาะ key ที่อยู่ข้างในช่วงจริง ๆ (พิสูจน์แล้วบนช่วงที่เริ่มกลางซูมเด้งและกลางซูมช้า)
  - ไม่มีเวลาติดลบ
  - ช่วงที่เริ่มหลัง punch จบแล้วได้ค่า 1.15 ค้างทั้งช่วงพอดี
- **ทาง CapCut:** คัดลอก key ตรงตัว (§8)
- id ใหม่ทุกระดับ
- เทสต์ทั้งสองทาง:
  - ช่วงที่อยู่หลัง punch ที่จบแล้ว
  - ช่วงที่อยู่ใน drift
  - ช่วงที่จบกลาง punch
  - ช่วงที่จบตรงท้ายชิ้นใต้ drift ที่ key สุดท้ายเลยท้ายชิ้น ~7 ms

### 9.4 ตัวเลข

- `HighlightPreview.behindPerson = { laid, front, pending, covered }`
- `WriteResult.behindPerson = { laid, front, covered }`
  - `laid`: ชุดที่อยู่หลังคนจริง (ทาง CapCut ไม่ต้องรอ จึงนับเป็น laid ทันที)
  - `front`: ชุดที่ป้ายมีผลแต่ถูกวาดไว้หน้า รวมกรณีที่รู้ก่อนตัด เช่นต้นฉบับไม่รองรับหรือไม่มีตัวตัด
  - `pending`: ชุดที่งานยังไม่จบ (มีเฉพาะในตัวอย่าง)
  - `covered`: ชุดที่มีคำเตือนหัวบัง
  - ปิดสวิตช์รวม หรือระดับซ่อนชุดนั้น: ไม่นับทุกช่อง
- ตัวอย่างเท่ากับที่เขียนเมื่อ `pending` เป็น 0 ถ้า `pending` > 0 การเขียนจะรอก่อน แล้วตัวเลขที่เขียนคือผลหลังรอ
- `dropped.cutouts` นับชิ้นตัวคนที่ถูกข้ามเพราะสั้นกว่าหนึ่งเฟรม ชุดที่เหลือช่วงอื่นยังนับเป็น laid
  - `LaidKind` และ `DROPPED_NAMES` เพิ่มชนิดนี้

## 10. คำเตือนหัวบัง

1. เลือกสามเวลาบนไทม์ไลน์ของชุด: เฟรมแรก กลาง และสุดท้ายที่ชุดขึ้นจอ แล้วแปลงเป็นชิ้นหลักและเฟรมต้นฉบับ
2. ใช้ `boxblack-segment sample` กับเฟรมเหล่านั้น
   - เป็นงานเล็กในคิวเดียวกัน (§7.3) ลำดับก่อนงานตัด
   - cache ตาม path ขนาด เวลาแก้ของต้นฉบับ และเลขเฟรม ไว้ใน `cutouts/samples/` การแก้คำหรือลุคจึงคำนวณใหม่ได้โดยไม่ต้องรัน Vision
3. แปลง mask เข้าพิกัดของจอด้วย `clip` ของชิ้นหลัก (scale, transform, การปรับให้เต็มจอ) และค่าซูม `value(t)` ณ เวลานั้น
4. กรอบของแต่ละบรรทัดมาจาก `LaidLine` (y, scale, x รวมการเยื้องของแบบบันได)
   - กว้าง = `textUnits × LINE_WIDTH_RATIO × scale`
   - สูง = ความสูงบรรทัดของ layout
5. บัง = สัดส่วน pixel ในกรอบที่ mask ≥ 0.5 ใช้ค่ามากสุดจากสามเวลา
6. บรรทัดใดบังเกิน **35%** ชุดนั้นมีคำเตือน "หัวบังข้อความมาก อาจอ่านไม่ออก" และนับเป็น `covered`
   - 35% เป็นค่าเริ่มต้น ปรับได้ตอนทดสอบจริง
   - แอปไม่ย้ายตำแหน่งเอง
- ใช้ทั้งสองทาง ถ้าไม่มีตัวตัด สถานะบอกว่า "ตรวจหัวบังไม่ได้ (ไม่มีตัวตัด)" และไม่นับ `covered`
- การเขียนรองาน sample ด้วย ตัวเลขจึงตรงกับตัวอย่าง
